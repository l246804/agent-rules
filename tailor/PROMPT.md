# 给本地 agent 的提示词：把融合规则集裁剪进本项目

> 用法：在目标项目里打开你的编码 agent（Claude Code / Codex / DSH / Cursor 等），把下面 **冒号后的全部内容** 粘进去；把 `<RULES_DIR>` 替换成本仓库的实际路径（例如 `/home/leihaohao/workspace/agent-rules`）。无需其他工具；若该目录里有 `tools/tailor.mjs`，优先用它生成（结果稳定）。

---

你要把一份**四源融合的 AI 编码代理规则集**裁剪成本项目适用的 `AGENTS.md`。规则源：`<RULES_DIR>/AGENTS.merged.md`（10 节 48 条，每条带 `[P/K/H/S:path:line]` 出处）；裁剪档定义在同文件的**附录 A**；可运行的裁剪器：`<RULES_DIR>/tools/tailor.mjs`（Node ≥18，无依赖）。

## 第 1 步：侦察项目（只读，先不要写任何文件）

收集并向我复述：

1. 项目形态：单包 / monorepo（是否有 `packages/`、workspaces）、语言与框架、包管理器；
2. 是否已有 `AGENTS.md` / `CLAUDE.md` / `.cursor/rules/*`；若有，**逐条列出其中的项目专属规则**（这些必须保留）；
3. `AGENTS.md` 里是否存在工具自动注入的标记区间（如 `<!--VITE PLUS START-->`、`<!-- CODEX START -->` 等成对的注释标记）——**不要改动这些区间**；
4. 是否有 CI 配置（`.github/workflows/`、`.gitlab-ci.yml`、pipeline 文件）→ 决定 CI 矩阵 = yes/no；
5. 是否配置了提交钩子且会在 staged/commit 阶段自动改写文件（如 husky/lint-staged/lefthook/`vp config`）→ 若"是"，建议追加 `machine-block` 片段；
6. 现有验证入口：格式化、lint、类型检查、测试命令的真实来源（package.json scripts / 构建工具配置），以及**同名命令与脚本语义是否不同**。

## 第 2 步：确定裁剪档（先问我，再决定）

| 场景 | profile | `--add` | `--ci` |
| --- | --- | --- | --- |
| 个人小项目 / 脚本 / 原型 | `minimal` | 无 | 按第 1 步 |
| 常规项目、单包应用 | `full` | 无（或 `machine-block`） | 按第 1 步 |
| 多包 monorepo、多团队协作 | `full` | `monorepo`（+ `machine-block`） | 通常 yes |
| 前端项目（路由/状态库/生成物） | `full` | `frontend`（+ `machine-block`） | 按第 1 步 |

给我一个推荐 + 理由，等我确认后再生成。

## 第 3 步：裁决 7 个条件条款

规则里有 7 条 ⟨条件式⟩ 条款（R1.4、R3.2、R3.3、R5.1、R5.3、R6.3、R9.3），来自四个来源的冲突。默认按以下裁决执行，**除非本项目的既有约定相反**：

1. R1.4 歧义：高风险/不可逆先问；其余取最合理默认值继续并在同一回复里声明假设；
2. R3.2 追溯：每行改动可追溯；根因修复扩大范围时在交付说明里点明；
3. R3.3 死代码：自己改动造成的孤儿必清；既有死代码只报告不删；
4. R5.1 依赖：默认爬梯；新增依赖需"能真正删掉自有代码与测试"或"原生确实不足"；
5. R5.3 配置：默认值不重复声明；随部署变化的取值必须是显式可校验的配置字段；
6. R6.3 测试重量级：有 CI 矩阵 → 交给 CI，本地只跑最窄证据；无 CI → 每个行为改动配最窄检查；
7. R9.3 兼容：已发布/持久化世代只新增版本化后继，不移动、不覆盖、不删除。

若项目已有约定与上述任一条冲突，把冲突点列出来问我，不要静默择一。

## 第 4 步：生成（两种方式，优先第一种）

```bash
# 方式 A（推荐，确定性强）
node <RULES_DIR>/tools/tailor.mjs --profile <minimal|full> \
  --add <monorepo,frontend,machine-block 里适用的> \
  --ci <yes|no> \
  --title "AGENTS.md" \
  --out AGENTS.md
```

方式 B（没有脚本时手工生成）：读 `<RULES_DIR>/AGENTS.merged.md`，按附录 A 保留对应小节与条款，逐条复制规则正文，**删掉所有 `[P/K/H/S:…]` 出处标签**（除非用户要审计轨迹），并把 7 条条件式按第 3 步写定。

**合并而非覆盖（最重要）**：

- 若项目已有 `AGENTS.md`：把生成内容与既有内容合并——项目专属规则优先保留，框架/工具链/目录约定不要被通用条款覆盖；重复的语义合并成一条（保留更具体的措辞）；
- 若文件里有机器管理标记区间：只在区间之外增改；
- 生成后用 `diff`/并排预览给我看，**等我确认再落盘**；
- 不要动 `CLAUDE.md` 等软链/派生文件的链接关系（若 `CLAUDE.md` 是指向 `AGENTS.md` 的软链，只改真实文件）。

## 第 5 步：自检（逐条报告结果）

1. 产物里**不残留** `[P:`、`[K:`、`[H:`、`[S:`、`findings/` 等出处标签（除非我要求保留）；
2. 条款编号唯一（无重复 `R*.*`），小节编号连续；
3. `minimal` 档为 19 条核心（§1、§2、§3、§4 各取关键条款 + R5.1 + R6 的四条 + §7 + R9.4 R9.5）；`full` 档含 §0–§9 全部 48 条；
4. 追加片段按 `--add` 顺序编号为 §10、§11…，且不含被剔除非规则内容；
5. 项目既有规则一条不丢（列一个"保留清单"）；
6. 机器标记区间内容**逐字节未变**（可用 `git diff` 证明只改了区间外内容）；
7. 文件以恰好一个换行结尾；
8. 报告你实际运行过的命令（没跑的就不要声称跑过）。

## 第 6 步：交付说明（≤10 行）

- 裁剪档与追加片段、CI 取值；
- 7 条条件式的裁决结果（与项目冲突的已列明）；
- 合并时做了哪些取舍（保留/合并/丢弃各是什么、为什么）；
- 未采纳的规则与理由（例如"本项目无 monorepo 结构，未追加 monorepo 片段"）。
